# Human Test Checklist: same-name guard and move delete-gate (0.9.1)

**Target version:** dazzle-preservelib 0.9.1
**Ships with commit:** `fix(0.9.1): a move never destroys a same-named source; re-check the destination before deleting` (TBD hash)
**Companion automated tests:** 10 in `tests/test_same_name_guard.py`; full suite 226 passed, 3 skipped (Windows).

## What this is

Before 0.9.1, moving two files with the same name into one folder with flat paths and an overwrite-class policy (dazzlecmd's `dz f-mv -f a/x.txt b/x.txt dest/`) copied a, copied b over it, then deleted both sources -- a's content existed nowhere, and the command reported success. 0.9.1 refuses the second source and leaves it in place, and a move re-checks each destination's bytes right before deleting its source. This checklist drives the real CLIs (`dz f-mv`, `dz f-cp`, `preserve COPY/MOVE`) through those cases on throwaway files, to confirm what the unit tests cannot: real exit codes, real messages, real files.

## Prerequisites

1. `dz` (dazzlecmd) installed, and the 0.9.1 source checked out. If 0.9.1 is not yet installed, point Python at the checkout for the session (the variable outranks an installed or editable copy):

   **cmd.exe:** `set PYTHONPATH=<path to the 0.9.1 checkout>`
   **PowerShell:** `$env:PYTHONPATH = "<path to the 0.9.1 checkout>"`
   **POSIX:** `export PYTHONPATH=<path to the 0.9.1 checkout>`

   Confirm which copy loads (all shells): `python -c "import dazzle_preservelib as p; print(p.__file__)"` -- it must print a path inside the 0.9.1 checkout.
2. A scratch folder. Everything below happens inside it; nothing outside it is touched.

   **cmd.exe:** `mkdir %TEMP%\samename && cd /d %TEMP%\samename`
   **PowerShell:** `New-Item -ItemType Directory $env:TEMP\samename | Out-Null; Set-Location $env:TEMP\samename`
   **POSIX:** `mkdir -p /tmp/samename && cd /tmp/samename`

3. **Fixture (run before EACH test; it resets the case):** a folder per test, two sources named `x.txt` with different contents, an empty `dest`. Cross-shell via Python:

   ```
   python -c "import pathlib,sys; d=pathlib.Path(sys.argv[1]); [ (d/p).parent.mkdir(parents=True, exist_ok=True) for p in ('a/x.txt','b/x.txt','dest/.keep') ]; (d/'a/x.txt').write_text('AAA'); (d/'b/x.txt').write_text('BBB')" CASE
   cd CASE
   ```
   (replace `CASE` with the test's id, e.g. `hv1`). To read the results (all shells): `python -c "import pathlib; [print(p, '=', p.read_text() if p.exists() else '(absent)') for p in map(pathlib.Path, ('a/x.txt','b/x.txt','dest/x.txt','dest/x_001.txt'))]"`

## High-Value Verification (~5 minutes)

### HV.1 -- `f-mv -f` no longer destroys the first file

- [ ] **Steps:** fixture `hv1`; `dz f-mv -f a/x.txt b/x.txt dest/`; read the results.
- [ ] **Expected:** a line `[FAIL] b\x.txt: will not overwrite dest\x.txt, which this operation just placed from another source with the same name; b\x.txt was left in place (use --on-conflict rename to keep both)`; exit code 3. Files: `a/x.txt (absent)`, `b/x.txt = BBB`, `dest/x.txt = AAA`.
- [ ] **Why this matters:** this is the data-loss case; on 0.9.0 both sources vanish and `dest/x.txt = BBB`.

### HV.2 -- `rename` keeps both

- [ ] **Steps:** fixture `hv2`; `dz f-mv --on-conflict rename a/x.txt b/x.txt dest/`.
- [ ] **Expected:** `[OK] ... processed=2`, exit 0; `dest/x.txt = AAA`, `dest/x_001.txt = BBB`; both sources gone.
- [ ] **Why this matters:** the message in HV.1 tells the user to use rename; it must work.

### HV.3 -- `-f` still overwrites a file that was there before

- [ ] **Steps:** fixture `hv3`; put a pre-existing file in place: `python -c "open('dest/x.txt','w').write('OLD')"`; then `dz f-mv -f a/x.txt dest/`.
- [ ] **Expected:** exit 0; `dest/x.txt = AAA`; `a/x.txt (absent)`.
- [ ] **Why this matters:** the guard must not change `-f`'s documented meaning for existing files.

### HV.4 -- `f-cp -f` keeps the first copy

- [ ] **Steps:** fixture `hv4`; `dz f-cp -f a/x.txt b/x.txt dest/`.
- [ ] **Expected:** the same refusal line for `b\x.txt`; exit 5; sources intact; `dest/x.txt = AAA`.
- [ ] **Why this matters:** on 0.9.0 the copy silently replaced the first file.

### HV.5 -- the import-origin guard in the test suite

- [ ] **Steps:** from a directory OUTSIDE the 0.9.1 checkout, with `PYTHONPATH` unset, run `python -m pytest <checkout>/tests`.
- [ ] **Expected (only when another copy of preservelib is installed, e.g. editable elsewhere):** the run stops at collection with `dazzle_preservelib imported from <other path>, not from this checkout (<checkout>). Run with PYTHONPATH=<checkout>.` With `PYTHONPATH` set to the checkout, the suite runs.
- [ ] **Why this matters:** without it a worktree run silently tests a different copy.

## Section 1: every conflict policy, two same-named sources (`dz f-mv`)

Fixture per row; run `dz f-mv <flags> a/x.txt b/x.txt dest/`.

| Flags | Expected files | Expected exit |
|---|---|---|
| (none -- default `fail`) | a moved; `b/x.txt = BBB`; `dest/x.txt = AAA`; refusal line for b | 3 |
| `-n` (skip) | a moved; `b/x.txt = BBB`; `dest/x.txt = AAA`; b reported skipped | 0 or skip-coded |
| `--on-conflict newer` (touch b to be newer first) | as `-f`: b refused and kept | 3 |
| `--on-conflict larger` (make b longer first) | as `-f`: b refused and kept | 3 |

- [ ] each row matches; in no row does `AAA` disappear.

## Section 2: the preserve CLI

- [ ] **COPY:** fixture `p1`; `preserve COPY --flat --on-conflict overwrite --dst dest a/x.txt b/x.txt`. Expected (observed at release prep): the refusal line for `b\x.txt`; summary `Failed: 1`; exit 1; `dest/x.txt = AAA`; sources intact.
- [ ] **MOVE:** fixture `p2`; `preserve MOVE --flat --on-conflict overwrite --dst dest a/x.txt b/x.txt`. Expected (observed): the refusal line; summary `Copy failed: 1`, `Successfully MOVED (source deleted): 1`; exit 1; `dest/x.txt = AAA`; `a/x.txt (absent)`; `b/x.txt = BBB`.
- [ ] **RESTORE after MOVE** (not yet run at release prep): `preserve RESTORE --src dest --dry-run`, then without `--dry-run`. Expected: a returns to `a/x.txt`; nothing claims b, which never moved.

## What the automated tests DON'T cover

- Real exit codes and messages from `dz f-mv` / `f-cp` and `preserve`, and how they render in each shell.
- dazzlecmd's summary line: after a partial move it still prints `verify failed -- source preserved (no deletion occurred)`, which is false for the source that did move. Known; fixed on the dazzlecmd side in 0.12.25. Note whether it still appears.
- Case-insensitive collisions on Windows (`A/X.txt` and `b/x.txt`): the guard compares destinations case-insensitively there. Try it.
- Long paths, network shares, and sources on different volumes.
